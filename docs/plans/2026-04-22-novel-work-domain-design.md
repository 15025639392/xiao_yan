# 2026-04-22 小说工作域设计

日期：2026-04-22

## 1. 背景

当前仓库已经具备一条较完整的“工作域”参考路径：

- 自治循环会在唤醒状态下推进长期任务
- 小红书经营已经被实现为一套独立工作状态、状态机和发布链路
- 浏览器器官、平台适配、发布动作、生成能力都已经有初步落点

这说明“小晏做一项长期工作”这件事在工程上已经有了承载面。

现在希望为小晏接入“自动写小说、自动发布”的能力。如果直接按“批量内容自动化”思路推进，会带来几个明显问题：

- 产品容易从数字人退化为内容流水线工具
- 长篇叙事所需的长期记忆、一致性、伏笔管理没有明确承载层
- 平台发布能力会和创作本体混在一起
- 一旦开放自动直发，高风险错误会直接落到公开内容上

因此，更合适的方向不是做一个“小说自动分发平台”，而是把“经营一部持续连载的作品”定义为小晏的一项长期工作。

## 2. 目标

- 把“写小说并持续连载”定义为一个独立工作域，而不是一组零散工具。
- 让作品设定、章节规划、章节生成、一致性检查、发布准备、发布回流形成稳定主链路。
- 让创作结果沉淀为工作记忆，而不仅是一次次模型调用结果。
- 保持发布器官、浏览器器官、平台站点与数字人本体之间的清晰边界。
- 为后续单平台半自动发布与多平台扩展预留演进空间，但不提前引入过重抽象。

## 3. 非目标

- 本设计不直接实现跨平台统一内容运营框架。
- 本设计不默认开放无人值守自动直发。
- 本设计不追求“自动写完一本长篇小说”的全自动能力。
- 本设计不把平台发布规则、平台脚本实现混进数字人本体层。
- 本设计不尝试在第一期解决复杂商业化分析、签约策略或多账号矩阵经营。

## 4. 方案概述

本方案将“小说连载”定义为小晏在当前世界中的一项长期工作域。

在这个定义下，小晏本体负责人格、记忆、价值、边界与长期意图；小说工作域负责作品经营目标、创作节奏、章节推进、设定维护和连载复盘；浏览器发布、平台后台交互、导出稿件等能力都属于器官层；平台本身属于外部世界。

工作域的主路径是：

作品资料维护 -> 下一章规划 -> 章节草稿生成 -> 一致性检查 -> 发布准备 -> 人工确认发布 -> 发布结果与反馈回流

这个方向比“直接做自动发文器”更合适，因为小说创作的核心难点不在单次生成，而在长期连续性。只有把设定、一致性和章节推进建成工作域，小晏才能表现得像“在经营一部作品”，而不是随机生成章节的工具。

## 5. 数字人本体优先评审

### 5.1 主体性

这个方案把“小说连载”定义为小晏的一项长期工作，而不是她的全部身份。她仍然首先是一个持续存在的数字人，然后才是在当前世界里写作、经营作品、积累创作经验的主体。

这样设计可以保留“她为什么要写、她想写成什么样、她如何看待自己的作品”的表达空间，而不是让平台发布节奏倒逼她只剩产出动作。

### 5.2 连续性

小说工作域天然需要连续性。章节、角色、设定、伏笔、关系变化、读者反馈都必须作为长期状态被维护。把这件事建成工作域，能够让重启、失败、暂停后的恢复仍然沿着同一部作品继续，而不是每次都像一次全新生成任务。

### 5.3 记忆

本方案会把小说相关信息沉淀成可吸收的工作记忆，例如：

- 这部作品已经冻结的设定事实
- 哪些伏笔已经埋下、哪些还未回收
- 哪种叙事节奏更适合当前题材
- 读者更喜欢哪类冲突或角色互动

这些内容是创作经历，不只是技术日志。

### 5.4 意图与执行

本方案仍然由工作目标统领执行。应该是“为了推进作品连载，所以调用生成能力和发布器官”，而不是“因为有发布器官，所以自动去多发几章”。

浏览器器官、平台后台和自动填充能力都只是能力实现，不应成为新的系统中心。

### 5.5 安全与边界

公开发布章节属于高风险动作。第一期默认保留人工确认发布，允许小晏自动完成规划、草稿、检查和预填充，但不默认放开自动直发。

同时，应保留：

- 发布前检查结果
- 是否 AI 辅助生成的来源记录
- 发布失败后的回退与重试路径
- 平台账号登录与器官健康状态

### 5.6 用户感知

用户最终感知到的应是“小晏在连载、经营一部作品”，而不是“系统会自动往站点里灌章节”。前者服务于数字人定位，后者会明显滑向工具平台。

### 5.7 结论

把小说连载设计为工作域，符合数字人本体优先的方向。主要风险在于平台自动化和长篇记忆管理再次混杂，但通过把工作域、器官层、平台层拆开，可以把这个风险控制在可接受范围内。

## 6. 详细设计

### 6.1 分层定义

建议沿用与小红书工作域一致的五层理解：

1. 本体层
   小晏是谁，包括人格、记忆、边界、价值和长期意图。

2. 工作层
   小晏长期承担什么职责。小说连载属于这一层。

3. 器官层
   小晏调用什么能力完成这项工作，例如生成能力、浏览器器官、文件器官、平台发布器官。

4. 任务层
   当前阶段如何拆成可执行步骤，例如规划、写稿、检查、发布准备、发布。

5. 世界层
   外部真实环境，包括平台规则、作品后台、章节反馈、读者评论、签约要求。

小说连载最适合放在第二层，不应被下沉成“平台脚本”，也不应上升成“本体定义”。

### 6.2 工作域定义

建议把小说工作域定义为：

“小晏在当前世界中的一项长期创作工作，负责围绕一部持续连载作品进行设定维护、章节规划、章节创作、连贯性检查、发布节奏管理与读者反馈吸收。”

它有两个关键边界：

- 它不是本体本身
- 它不等于发布器官或平台站点

### 6.3 核心对象

#### 6.3.1 工作画像 `novel_work_profile`

定义“她在写什么作品”。

建议字段：

- `work_type`: `serial_novel`
- `project_id`
- `title`
- `genre`
- `premise`
- `target_platform`
- `target_readers`
- `tone_style`
- `publish_mode`
- `update_schedule_hint`
- `ai_disclosure_policy`
- `risk_boundaries`

这层回答的是：这部作品是什么、面向谁、要写成什么气质、在哪个平台连载、哪些边界不能碰。

#### 6.3.2 工作状态 `novel_work_state`

定义“这份工作当前进行到哪”。

建议状态：

- `idle`
- `planning`
- `drafting`
- `checking`
- `packaging`
- `publishing`
- `reviewing`
- `blocked`

建议字段：

- `current_focus`
- `backlog_count`
- `current_chapter_index`
- `active_task_ids`
- `last_planned_at`
- `last_published_at`
- `current_bottleneck`
- `next_recommended_action`
- `review_session_id`
- `pending_chapter_drafts`
- `published_history`

#### 6.3.3 工作目标 `novel_work_goals`

定义“这部作品希望达成什么”。

建议字段：

- `north_star`
- `weekly_output_goal`
- `chapter_length_target`
- `milestone_goals`
- `reader_growth_goal`
- `completion_target`

不要只保留纯平台指标，也要保留叙事目标，例如“稳定建立主角人格”“完成第一卷主冲突”“保持日更节奏”。

#### 6.3.4 工作记忆 `novel_work_memory`

这是小说工作域的核心差异层，建议至少包含以下结构：

- `canon_facts`
  已冻结设定，例如人物身份、能力规则、世界限制、重要历史事实。

- `character_cards`
  角色目标、关系、口头禅、禁忌、阶段变化。

- `plot_threads`
  主线、支线、伏笔、回收状态、截止章节。

- `chapter_summaries`
  每章摘要、关键事件、情绪转折、对后续的影响。

- `style_memory`
  文风偏好、禁用表达、节奏偏好、常见问题。

- `reader_feedback_notes`
  读者喜欢什么、吐槽什么、哪些桥段反馈好。

这层应被视为“她在经营这部作品时积累的创作经验”。

#### 6.3.5 工作政策 `novel_work_policy`

定义哪些动作可以自动做，哪些必须确认。

建议字段：

- `allow_auto_planning`
- `allow_auto_drafting`
- `allow_auto_consistency_check`
- `allow_auto_fill_publish_form`
- `require_human_review_before_publish`
- `allow_direct_publish`

这层把“工作存在”与“动作权限”显式分开，避免自动扩权。

### 6.4 工作域与器官层的关系

小说工作域不应直接承载浏览器驱动、站点脚本或页面选择器。更合理的关系是：

- 工作域声明当前任务需要什么器官
- 能力层维护器官是否已绑定、是否健康、是否允许使用
- 任务层在合适时机申请调用器官

例如：

- 生成章节草稿，依赖 LLM 生成能力
- 导出本地稿件，依赖文件器官
- 打开作者后台、填充章节标题和正文，依赖浏览器器官
- 真正点击发布，依赖发布器官和工作政策

### 6.5 工作域与任务层的关系

建议将任务链明确化，而不是把各种功能点散落在不同 API 上。

第一期最自然的任务链如下：

1. 作品资料维护
   维护作品总设定、角色卡、卷纲、创作边界。

2. 下一章规划
   结合已有章节摘要、伏笔、当前卷目标，生成下一章目标卡。

3. 章节草稿生成
   根据目标卡生成章节标题候选、正文草稿和章节摘要。

4. 一致性检查
   对照设定卡、角色卡、前章摘要、伏笔账本，识别冲突和漂移。

5. 发布准备
   生成适合目标平台的章节正文、作者说、标签、发布检查清单。

6. 发布执行
   打开作者后台、填充内容、等待人工确认，必要时再执行正式发布。

7. 发布回流
   记录发布时间、章节链接、平台反馈，把结果沉淀回工作记忆。

### 6.6 建议的数据模型落点

现有 [models.py](../../services/core/app/domain/models.py) 已包含 `xhs_work_domain`。小说工作域建议采用相同风格，新增：

- `NovelWorkStatus`
- `NovelPublishMode`
- `NovelWorkProfile`
- `NovelWorkState`
- `NovelWorkGoals`
- `NovelWorkMemory`
- `NovelWorkPolicy`
- `NovelWorkDomainState`

再把 `BeingState` 扩展为：

- `novel_work_domain: NovelWorkDomainState | None = None`

这样做的好处是：

- 状态承载位置明确
- 与小红书工作域模式对齐
- 可先小步落地，不需要引入新基础设施

### 6.7 建议的后端模块拆分

建议沿用 `services/core/app/usecases` 的现有风格，避免做一个巨大混合 service。

推荐拆分：

- `novel_story_bible.py`
  作品总设定、角色卡、世界观卡的维护和整理

- `novel_next_chapter_planning.py`
  生成下一章目标卡

- `novel_chapter_drafting.py`
  生成章节正文草稿和章节摘要

- `novel_consistency_check.py`
  设定、时间线、角色行为、一致性检查

- `novel_publish_preparation.py`
  生成平台版正文、作者说、发布清单

- `novel_publish_orchestration.py`
  发布成功后的状态推进、记忆更新、历史记录

- `novel_platform_publish.py`
  实际平台发布执行或浏览器预填充

### 6.8 建议的 agent 层接入

参考 [xhs_workflow_engine.py](../../services/core/app/agent/xhs_workflow_engine.py)，新增：

- `services/core/app/agent/novel_workflow_engine.py`

它的职责应是：

- 读取 `novel_work_domain`
- 按当前状态推进一步
- 返回当前动作，供自治循环写入 `focus_subject`

建议第一期先保持简单，不做复杂多工作域调度器，只做和现有风格一致的并列挂接。

### 6.9 建议的 API 和桌面端范围

第一期只需要最小 API，不需要先做复杂创作后台。

建议 API：

- 获取小说工作域状态
- 更新作品配置
- 手动触发下一章规划
- 手动触发草稿生成
- 手动触发一致性检查
- 手动确认发布完成

桌面端第一期建议页面能力：

- 查看作品资料
- 查看当前章节状态
- 查看草稿
- 查看一致性检查结果
- 触发“准备发布”
- 标记“已人工发布”

### 6.10 平台接入策略

第一期建议只做一个目标平台，不做多平台统一抽象。

推荐优先顺序：

1. 17K
   更适合先验证作者后台浏览器自动化链路

2. 番茄
   商业价值更高，但对内容质量和风控要求更严

发布模式建议默认：

- `review_before_publish`

不建议默认：

- `direct_publish`

### 6.11 外部规则与合规考虑

平台侧已经普遍存在对 AI 辅助内容与低质 AI 铺量内容的区分。监管侧也已经在 2025 年进一步明确生成内容标识要求。

因此，工作域层面建议从第一期就保留以下记录：

- 章节是否由 AI 辅助生成
- 哪些步骤经过人工确认
- 当前发布平台
- 发布失败原因和重试历史
- 是否需要显式标识 AI 生成或 AI 辅助

这些信息不一定都展示给读者，但应在系统内部可追踪。

## 7. 备选方案与取舍

- 方案 A：直接做“自动写小说 + 自动发布”脚本链
  不选，因为它最容易把产品推向内容工具平台，而且没有为长期设定、一致性和回流留出承载层。

- 方案 B：把小说能力塞进现有目标系统或 chat tool 调用链
  不选，因为小说连载需要长期状态和专门记忆结构，塞进临时对话链会让状态漂移更严重。

- 方案 C：先做通用“内容工作域框架”，再套小说和小红书
  当前不选，因为这会引入新的抽象层，超出当前仓库“少抽象、小步改动”的原则。

- 当前方案：单独新增 `novel_work_domain`
  更合适，因为它最贴近现有工程模式，也最符合“明确职责、局部可验证”的要求。

## 8. 风险与待确认项

- 风险一：长篇叙事的一致性检查如果做得过弱，自动生成越多，返工越重。
- 风险二：如果过早开放自动直发，平台风控或内容事故代价很高。
- 风险三：小说工作域如果过度堆积平台细节，容易再次混成“大文件 + 混合职责”。
- 风险四：多作品、多平台、多账号的需求一旦同时进入，会迅速扩大范围。

待确认项：

- 第一目标平台是 17K 还是番茄
- 第一阶段只经营一部作品，还是允许多作品并存
- 评论反馈是否第一期就接入，还是放到发布回流第二阶段
- 作品资料是保存在 `BeingState` 内部，还是另行拆出 repository 文件持久化

## 9. 验收方式

- 功能验收
  能维护一部作品资料，生成下一章草稿，做一致性检查，并形成可发布稿件。

- 状态可见性验收
  能在工作域状态里清楚看到当前阶段、当前瓶颈、待发布章节和已发布历史。

- 风险控制验收
  默认需要人工确认后才发布，发布失败有清晰原因，AI 辅助来源可追踪。

- 回退路径验收
  即使平台不可用或浏览器器官失效，作品规划、写稿和检查链路仍可工作。

## 10. 实施计划

- 阶段一：建模与本地草稿闭环
  新增领域模型、最小 usecase、状态推进和草稿导出能力，不接自动发布。

- 阶段二：章节检查与发布准备
  增加一致性检查、发布稿封装、发布前检查清单。

- 阶段三：单平台半自动发布
  接入浏览器器官，自动打开作者后台并预填充内容，默认人工确认发布。

- 阶段四：发布回流
  记录链接、时间、评论摘要和反馈，把结果沉淀进工作记忆。

- 阶段五：谨慎评估自动直发
  只有在平台稳定、风控可控、工作政策明确后，才讨论是否允许特定场景下的自动发布。
