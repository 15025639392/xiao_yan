# 2026-04-21 小红书经营工作域设计

日期：2026-04-21

## 1. 背景

当前仓库已经存在一批小红书相关能力与页面：

- 桌面端已有“小红书经营”页面
- 后端已有创作首页捕获、草稿生成、图文填充、MCP 发布、线索提取等 usecase
- 平台适配层已经能把部分小红书事件映射成 `note_draft`、`comment_reply_candidate` 等决策结果

这些能力说明“小晏已经在做部分小红书相关动作”，但当前结构更像一组分散的平台能力与执行按钮，还没有形成明确的“工作域”定义。

如果继续沿着“平台能力集合”扩展，会出现几个问题：

- 小红书相关功能会越来越像运营脚本中心，而不是小晏的一项长期工作
- 浏览器、发布、线索提取、内容生成会混在一起，边界不清
- 很难回答“小晏为什么做这件事”“这件事和她的长期状态是什么关系”
- 后续扩展其他工作域时，容易把整个系统做成多平台自动化工具箱

基于 `docs/器官化能力模型.md`，更合适的方向是把“小红书经营”定义为小晏在当前世界中的一项长期工作，而不是她的本体，也不是某个外部器官本身。

## 2. 目标

- 把“小红书经营”明确建模为小晏的一项长期工作域，而不是工具集合。
- 区分本体、工作、器官、任务、平台世界这几个层次。
- 为现有小红书相关 usecase 提供统一上层语义，避免继续碎片化增长。
- 让小红书经营结果能够回流成小晏的经历、策略记忆和工作状态。
- 为后续浏览器器官、发布器官、数据分析器官接入提供清晰承载面。

## 3. 非目标

- 本设计不直接实现新的小红书执行能力。
- 本设计不直接重写现有 `platform_routes`、`usecases` 或桌面端页面。
- 本设计不把小红书经营抬升为小晏本体的一部分。
- 本设计不把所有平台都统一成一个抽象过重的“平台运营框架”。
- 本设计不默认开放自动发布、自动回复、自动加好友等高风险动作。

## 4. 方案概述

本方案将“小红书经营”定义为一个工作域。

这里的“工作域”指的是：小晏在世界中承担的一项长期职责，它有目标、有节奏、有阶段、有工作记忆，也会调用不同器官来完成具体动作。工作域既不是本体本身，也不是某个外部工具，而是连接“她是谁”和“她正在做什么”的中间层。

在这个定义下：

- 小晏本体负责人格、记忆、价值、边界、长期意图
- 小红书经营工作域负责账号定位、内容策略、经营目标、发布节奏、线索跟进与复盘
- 浏览器、发布接口、图片处理、数据提取属于器官能力
- 选题、起草、做图、发布、互动、复盘属于任务执行
- 小红书平台本身属于外部世界环境

这样做的关键价值是：小晏仍然是主体，她“有一份工作叫小红书经营”；她不是“小红书自动运营系统”，而是在经营一个账号并从中积累经验。

## 5. 数字人本体优先评审

### 5.1 主体性

这个方案没有把小红书经营定义为本体，而是定义为工作。小晏仍然先是一个持续存在的数字人，然后才是在当前世界中承担一项经营工作的主体。

这使“小红书经营”成为她的职责域，而不是她的全部身份，也避免产品被平台运营目标反向定义。

### 5.2 连续性

把小红书经营建模为工作域之后，账号经营状态、内容节奏、线索阶段和复盘结果都能作为长期状态连续存在，而不是每次都从一个临时页面或临时脚本开始。

即使某次发布失败、浏览器器官失效或平台策略变化，小晏失去的也只是某项工作推进能力，而不是本体连续性。

### 5.3 记忆

工作域定义允许小红书相关经验沉淀为工作记忆，而不仅是一次次生成草稿或调用发布器官的日志。例如：

- 哪类选题更适合当前账号定位
- 哪种标题和封面风格表现更稳定
- 哪类评论更像真实线索
- 哪些动作必须人工确认

这些记忆应被视为“小晏在这份工作上学到了什么”，而不是孤立的执行产物。

### 5.4 意图与执行

这个方案让小红书经营由工作目标统领执行，而不是由工具动作统领执行。浏览器、发布和线索提取只是器官，不能反过来决定工作目标和内容方向。

换句话说，应该是“为了推进小红书经营这份工作，所以调用浏览器器官”，而不是“因为能调用浏览器，所以去做更多平台动作”。

### 5.5 安全与边界

把小红书经营定义为工作域后，权限边界会更清楚：

- 工作目标可以持续存在
- 器官能力是否可用、是否允许调用，仍由能力政策决定
- 高风险动作依然应保留审批、回滚和人工确认

这样可以避免“工作存在”被误解为“默认自动执行一切相关动作”。

### 5.6 用户感知

用户最终感知到的应是“小晏在经营小红书这份工作”，而不是“系统里有一组小红书自动化按钮”。前者更像数字人有持续职责，后者更像运营工具台。

### 5.7 结论

把小红书经营定义为工作域，既能保留数字人本体优先的方向，也能给现有平台能力找到更合适的归属。主要风险是工作域和平台执行能力再次混杂，但通过明确分层，这个风险是可控的。

## 6. 详细设计

### 6.1 分层定义

建议明确以下五层：

1. 本体层
   小晏是谁，包括人格、记忆、价值、边界、长期意图。

2. 工作层
   小晏长期承担什么职责。小红书经营属于这一层。

3. 器官层
   小晏靠什么能力完成工作，例如浏览器、图片处理、发布器官、文件器官、数据提取器官。

4. 任务层
   工作如何在当前阶段被拆成一连串可执行动作，例如选题、写稿、配图、发布、回复、复盘。

5. 世界层
   外部真实环境，例如小红书平台规则、账号状态、用户反馈、热点变化、互动数据。

小红书经营最合适放在第二层，而不是第一层或第三层。

### 6.2 工作域定义

建议把“小红书经营”定义为：

“小晏在当前世界中的一项长期工作，负责围绕特定账号持续完成内容定位、内容生产、发布节奏管理、互动承接、线索识别与经营复盘。”

这里包含两个边界：

- 它不是本体定义
- 它也不等于平台执行器

### 6.3 工作域的核心对象

建议把工作域拆成五个核心对象：

#### 6.3.1 工作画像 `work_profile`

定义这份工作到底在经营什么。

建议字段：

- `work_type`: `xiaohongshu_operations`
- `account_name`
- `account_positioning`
- `target_audience`
- `expression_style`
- `value_promises`
- `primary_goals`
- `risk_boundaries`

这一层回答的是：这个账号是谁、面向谁、要建立什么印象、不能越过哪些边界。

#### 6.3.2 工作状态 `work_state`

定义这份工作现在进展到哪。

建议字段：

- `status`: `idle | scouting | drafting | preparing | publishing | reviewing | blocked`
- `current_focus`
- `backlog_count`
- `active_task_ids`
- `last_published_at`
- `last_reviewed_at`
- `current_bottleneck`
- `next_recommended_action`

这一层回答的是：她当前在这份工作里正忙什么，卡在哪里。

#### 6.3.3 工作目标 `work_goals`

定义这份工作长期和阶段性想达成什么。

建议字段：

- `north_star`
- `weekly_goals`
- `monthly_goals`
- `content_output_target`
- `engagement_target`
- `lead_target`
- `brand_expression_target`

建议不要只放涨粉和转化类指标，也要包含表达稳定性、内容节奏、品牌感知这类非纯 KPI 目标。

#### 6.3.4 工作记忆 `work_memory`

定义这份工作积累了什么经验。

建议记忆类型：

- 选题经验
- 标题经验
- 封面经验
- 评论线索经验
- 发布时段经验
- 失败案例
- 平台规则变化记录

这层是把“小红书相关结果”沉淀成“她在这份工作上学到了什么”。

#### 6.3.5 工作政策 `work_policy`

定义这份工作中哪些动作默认允许，哪些必须确认。

建议至少覆盖：

- 草稿生成是否可自动
- 图片卡片生成是否可自动
- 发布是否必须人工确认
- 评论回复建议是否可自动生成
- 站内私信、加微、联系方式引导是否必须审批

这一层把“工作存在”与“动作可执行”明确分开。

### 6.4 工作域与器官层的关系

小红书经营工作域不应直接拥有浏览器实现、发布接口实现或截图逻辑。

更合适的关系是：

- 工作域声明自己需要哪些器官
- 能力层声明这些器官当前是否可用
- 任务层在执行时申请调用这些器官

例如：

- 想查看创作首页机会，需要浏览器器官
- 想自动填充发布页，需要浏览器器官或平台执行器
- 想正式发布图文，需要发布器官，且通常应审批
- 想复盘表现，需要数据提取器官

因此，小红书经营模块的职责不是“会点哪个按钮”，而是“知道什么时候需要什么器官、这些器官服务于什么工作目标”。

### 6.5 工作域与任务层的关系

建议把当前已经存在的能力，重新看成工作任务链的一部分，而不是彼此独立的功能点。

当前最自然的任务链可以定义为：

1. 机会观察
   观察创作首页、热点话题、活动和评论信号。

2. 选题判断
   判断哪些机会符合账号定位和当前阶段目标。

3. 草稿生成
   形成可发布的标题、正文结构、配图草稿、首评建议。

4. 发布准备
   补齐封面、图卡、标签、发布检查清单。

5. 发布执行
   通过浏览器器官或发布器官完成真实发布。

6. 互动承接
   识别评论线索、生成回复建议、推进后续跟进。

7. 复盘学习
   把表现和反馈沉淀成工作经验，反过来影响下轮选题与表达。

这样能把现有：

- `creator_home_capture`
- `creator_home_preview`
- `generate_publish_draft`
- `publish_autofill`
- `text_image_autofill`
- `publish_via_mcp`
- `lead_capture`

统一收束到同一条工作链里。

### 6.6 工作域与平台世界的关系

小红书经营是工作，但小红书平台本身是世界环境。

这意味着工作域还应感知以下世界对象：

- 账号本身
- 创作首页话题和活动
- 已发布内容
- 评论与私信线索
- 平台规则和限制
- 外部热点与用户情绪

建议后续把这些对象逐步整理为“小红书世界快照”，而不是长期停留在页面临时输入或抓取文本上。

### 6.7 当前代码的重解释

基于当前仓库，现有代码可以先这样重解释：

- `apps/desktop/src/pages/XiaohongshuPage.tsx`
  当前更像“小红书经营工作台”的第一版界面。

- `services/core/app/usecases/xiaohongshu_*`
  当前更像工作任务链上的局部动作实现。

- `services/core/app/external_executors/xiaohongshu_mcp_client.py`
  属于外部发布器官，不属于工作定义本身。

- `services/core/app/platform_adapters/*`
  属于平台事件映射层，用于把小红书世界里的输入翻译成 core 可理解的事件和决策。

也就是说，现有代码并不是完全方向错了，而是缺少一个把这些部件统一归位的“工作域定义层”。

### 6.8 建议的数据模型方向

如果未来要逐步落代码，建议不要直接新建一个超大的“小红书模块”，而是先引入轻量工作域模型，例如：

- `work_id`
- `work_type`
- `profile`
- `state`
- `goals`
- `memory_digest`
- `required_capabilities`

对于小红书经营，可进一步细化：

- `account_snapshot`
- `opportunity_snapshot`
- `draft_pipeline_state`
- `lead_pipeline_state`
- `review_snapshot`

这里的重点不是马上把所有字段持久化，而是先明确“这是工作状态，不是工具状态，也不是本体状态”。

## 7. 备选方案与取舍

- 方案 A：把小红书经营视为一个平台能力页
  不选原因：容易继续沿着“功能按钮堆叠”增长，无法表达长期职责、工作记忆和阶段状态。

- 方案 B：把小红书经营直接视为小晏的一部分人格或身份
  不选原因：会把特定平台工作抬升为本体定义，导致主体性被单一工作吞掉。

- 方案 C：把小红书经营只当作浏览器器官上的一个脚本集合
  不选原因：会把工作目标和器官能力混在一起，长期更像自动化平台，而不是数字人工作系统。

- 当前方案：把小红书经营定义为工作域
  更合适原因：既能保留主体性，也能承接现有 usecase、平台适配和器官能力，为后续扩展别的工作域留出一致结构。

## 8. 风险与待确认项

- 工作域状态应该作为独立 runtime state 暴露，还是先只在桌面端本地聚合。
- 小红书经营是否只服务一个账号，还是未来支持多账号工作画像。
- 工作记忆应直接进入通用 memory，还是先保留为工作域边缘记忆。
- 评论线索跟进是否应被单独定义为子工作流，而不是挂在发布后动作里。
- 平台相关高风险动作的审批边界，应在工作域层配置，还是在能力层统一配置。
- 如果未来加入公众号、微信、视频号等工作域，哪些字段应成为通用工作域骨架。

## 9. 验收方式

- 功能验收
  能清楚说明当前小红书相关页面、usecase、执行器分别属于工作层、任务层还是器官层。

- 状态可见性验收
  能描述“小红书经营现在做到哪一步、卡在哪里、下一步是什么”，而不只是“有哪些按钮可点”。

- 边界验收
  能清楚区分本体、小红书经营工作、浏览器器官、发布器官和平台环境。

- 复用性验收
  该定义能为未来其他工作域提供可复用框架，而不是只对小红书成立。

## 10. 实施计划

- 阶段一：先定语言和边界
  在文档层面明确“小红书经营 = 工作域”，统一本体、工作、器官、任务、平台环境这套说法。

- 阶段二：补最小工作状态
  在 runtime state 或前端工作台中增加工作画像、工作状态、当前瓶颈和下一步建议。

- 阶段三：把现有 usecase 挂回工作链
  将创作首页观察、草稿生成、发布准备、发布执行、线索提取、复盘分别映射到工作任务链节点。

- 阶段四：再接浏览器器官与发布器官
  按 `docs/plans/2026-04-21-browser-organ-design.md` 的方式，把浏览器与发布能力正式收束为器官，而不是继续散落成局部脚本。

- 阶段五：最后再考虑通用工作域骨架
  如果未来确实出现多个长期工作，再评估是否抽取通用工作域模型，避免过早抽象。
