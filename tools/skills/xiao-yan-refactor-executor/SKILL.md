# Xiao Yan Refactor Executor

在用户明确要“重构”“提取模块”“拆分文件”“迁移职责”“整理结构”时使用本 skill。

也接受以下短触发写法：

- `重构: <目标>`
- `重构执行: <目标>`
- `安全重构: <目标>`
- `拆分执行: <目标>`
- `只做小步重构: <目标>`

这个 skill 解决的是“怎么安全地改”，不是“要不要改”。

优先处理这几类动作：

- 提取 helper、assembler、adapter、presenter 等明确职责块
- 把混合职责文件拆成更小承载单元
- 把 route / service / repository 中越界的逻辑迁回边界
- 合并重复分支，保留原有行为
- 缩短过长调用链，但不引入新架构中心

默认不做：

- 全仓级重构
- 一次性改写整个领域
- 为未来假想扩展预埋抽象层
- 把重构包装成架构升级

## 必读上下文

开始前先读：

- `docs/AI 接手开发规范.md`
- 目标文件
- 直接入口、调用方、相关测试

如果入口还不明确，先用：

- `tools/skills/core-change-entrypoint/SKILL.md`

如果还没判断是否该拆，先用：

- `tools/skills/large-file-split-advisor/SKILL.md`

如果重构触到主流程、记忆、权限或运行时边界，先用：

- `tools/skills/xiao-yan-architecture-guardian/SKILL.md`

收尾前再补一轮：

- `tools/skills/docs-and-tests-sync-guard/SKILL.md`

## 低 Token 默认做法

默认只做当前需求必须落地的那一小段重构。

优先只改：

- 当前目标文件
- 新提取出来的最小承载文件
- 直接相关测试

默认不做：

- 借机统一同域全部命名
- 借机把整个目录结构重排
- 顺手把历史债务一次性清空

## 默认工作流

1. 先固定重构目标：
   - 提什么
   - 从哪里提
   - 提到哪里
   - 原行为哪些必须保持不变
2. 画出最小迁移链：
   - 现有入口
   - 中间调用层
   - 最终承载点
3. 选择执行模式：
   - `inline_cleanup`：原文件局部整理，不新增文件
   - `extract_helper`：提纯函数或小工具
   - `extract_module`：提一个明确职责模块
   - `move_boundary_logic`：把越界逻辑迁回应有层级
   - `two_step_refactor`：先兼容迁移，再清旧路径
4. 先做不改变行为的结构动作：
   - 提函数签名
   - 搬纯逻辑
   - 保留原接口
   - 让调用方先接新承载点
5. 再做收口动作：
   - 删除重复旧分支
   - 缩短原文件职责
   - 补测试和必要文档
6. 验证行为没有漂移：
   - 相关测试通过
   - 入口行为不变
   - 文件体积和职责边界没有变差

## 执行规则

- 能两步做完，就不要合成一步大改。
- 能保留旧接口过渡，就不要一口气改全链路签名。
- 新文件只承载一个清楚职责，不要新建“兜底 utils”。
- 如果原文件已经超预算，优先把新增或最混杂的那块逻辑提走。
- 如果重构需要跨很多层同时改，先降成 `two_step_refactor`，不要直接铺大改。

## 仓库专属提醒

- `services/core/app/api` 应保持协议层职责，不要把重构结果又塞回 route。
- `services/core/app/*/service.py` 可以做业务编排，但不要继续混存储细节和协议映射。
- 可选依赖相关逻辑应留在 adapter / repository 边缘，不要在重构过程中向核心扩散。
- 前端大页面或容器组件重构时，优先拆展示块或状态块，不要新增更深的共享抽象。
- 任何重构都不能让产品更像工具平台而不是数字人。

## 必须产出

- `重构目标`
- `原承载点`
- `新承载点`
- `执行模式`
- `改动顺序`
- `兼容策略`
- `验证方式`

推荐格式：

- `重构目标: 把 chat route 中的 response 组装提到独立 assembler`
- `原承载点: api route`
- `新承载点: chat assembler module`
- `执行模式: extract_module`
- `改动顺序: 先提取 assembler，再切调用，再删重复组装`
- `兼容策略: route 签名不变，响应结构不变`
- `验证方式: uv run --project services/core pytest ...`

## 收尾要求

- 如果改了结构或文件职责，运行 `python3 tools/check_file_budgets.py`
- 后端验证优先使用 `uv run --project services/core pytest ...`
- 结束时明确：
  - 大文件压力是降低了、持平了，还是变差了
  - 重复是减少了、持平了，还是新增了
  - 是否改到了性能敏感路径
  - 实际跑了哪些测试或检查

## 强约束

- 不要把重构升级成无边界的大整理。
- 不要静默引入新架构层、事件总线、队列、DI、ORM 或复杂配置层。
- 不要在一次重构里混入无关功能改动。
- 不要为了“更优雅”牺牲可追踪性和可回退性。
- 如果这轮重构已经触到架构边界，应先停下做边界判断，再继续执行。
