# Xiao Yan Code Optimizer

在用户要“优化代码”“提速”“减重复”“收敛职责”“顺手重构但别做大改”时使用本 skill。

也接受以下短触发写法：

- `优化: <目标>`
- `代码优化: <目标>`
- `优化分析: <目标>`
- `优化执行: <目标>`
- `只做最小优化: <目标>`

这个 skill 关注的是仓库内真实有价值的优化：

- 减少重复逻辑
- 缩短过长调用链
- 收紧模块职责
- 避免大文件继续恶化
- 修正明显低效热路径
- 收回泄漏的依赖或状态边界
- 补齐和优化动作直接相关的验证

不把“优化”默认解释成：

- 大范围架构重写
- 为未来做抽象
- 把数字人产品做成通用工具平台
- 顺手清理整仓无关问题

## 必读上下文

开始前先读：

- `docs/AI 接手开发规范.md`
- 涉及改动的目标文件
- 直接入口、调用方、相关测试

如果目标还是模糊的，先用：

- `tools/skills/core-change-entrypoint/SKILL.md`

如果优化会碰到核心运行时、记忆、目标、权限或主流程，再先用：

- `tools/skills/xiao-yan-architecture-guardian/SKILL.md`

如果目标文件已经偏大或混合职责明显，再先用：

- `tools/skills/large-file-split-advisor/SKILL.md`

如果涉及可选依赖、adapter、repository 或降级逻辑，再先用：

- `tools/skills/optional-dependency-boundary-check/SKILL.md`

优化完成后再补一轮：

- `tools/skills/docs-and-tests-sync-guard/SKILL.md`

## 低 Token 默认做法

默认只优化当前请求直接命中的那一条行为链。

优先只看：

- 当前目标文件
- 直接入口
- 直接依赖链
- 同域测试

默认不做：

- 全仓性能治理
- 大规模抽象收敛
- 无关模块顺手重构
- 一次性清理历史债务

## 默认工作流

1. 先定义这轮优化的真实目标：
   - 是减少重复
   - 降低复杂度
   - 修热路径
   - 收边界
   - 还是补验证缺口
2. 找到最小行为链：
   - 入口在哪
   - 数据或状态怎么流动
   - 哪一层正在承担不该承担的职责
3. 判断优化类型：
   - `keep_local`：局部整理即可
   - `extract_small_unit`：提纯函数、子模块或展示块
   - `remove_duplicate_branch`：合并重复逻辑
   - `tighten_boundary`：把依赖、状态或协议细节收回边界
   - `hot_path_fix`：减少重复扫描、重复请求、重复序列化或无界轮询
   - `split_before_optimize`：不先拆就会继续恶化
4. 优先选择最小可回退动作：
   - 先复用现有模式
   - 先局部收敛
   - 先移出明显不该待在这里的职责
5. 检查这轮优化有没有副作用：
   - 是否扩大改动半径
   - 是否引入新抽象层
   - 是否把可选能力抬成硬依赖
   - 是否让主链路更隐式
6. 只在必要范围内补测试、补文档、补验证命令。

## 优化判断规则

- 看到第二处相似逻辑时，先判断能否提取稳定共性。
- 文件大但职责单一，可以先局部优化，不强行拆。
- 文件已经大且这轮还要加新职责，优先视为 `split_before_optimize`。
- 性能优化优先修一眼可见的问题：
  - 循环里的重复 IO
  - 重复 HTTP 调用
  - 重复全量扫描或排序
  - 重复序列化 / 反序列化
  - 前端 render 里的重计算
- 如果一个“优化”主要是在增加抽象层、包装层、配置层，默认先否决。
- 如果两个方案都能工作，优先选更显式、更短调用链、更容易追踪和回退的方案。

## 仓库专属提醒

- `services/core/app/api` 不要继续吸收核心业务规则。
- `services/core/app/*/service.py` 不要同时承担决策、存储细节和协议映射。
- 可选依赖应继续留在边缘，不要因优化而扩散进核心路径。
- 前端页面和容器组件如果已经偏大，优化优先考虑提取明确职责块，而不是继续堆条件分支。
- 任何优化都要继续服务“小晏是数字人”这个方向，而不是把系统推向更通用的工具平台。

## 必须产出

- `优化目标`
- `行为链`
- `优化类型`
- `主要问题`
- `最小动作`
- `风险边界`
- `验证方式`

推荐格式：

- `优化目标: 降低 chat 路由中的重复组装逻辑`
- `行为链: api route -> service -> repository`
- `优化类型: remove_duplicate_branch`
- `主要问题: 两处分支重复拼装 response，后续继续改会双点漂移`
- `最小动作: 提取共享 assembler，保留 route 负责协议层`
- `风险边界: 不改返回结构，不改存储模型`
- `验证方式: uv run --project services/core pytest ...`

## 收尾要求

- 如果改动了结构或文件职责，运行 `python3 tools/check_file_budgets.py`
- 后端验证优先使用 `uv run --project services/core pytest ...`
- 结束时明确：
  - 大文件压力是降低了、持平了，还是变差了
  - 重复是减少了、持平了，还是新增了
  - 是否改到了性能敏感路径
  - 实际跑了哪些测试或检查

## 强约束

- 不要把“优化”当成顺手大重构许可。
- 不要静默引入新架构层、队列、DI、ORM 或重型框架。
- 不要在已经混合职责的热点文件里继续叠新逻辑。
- 不要只说“可优化”，要落到最小承载点和最小验证闭环。
- 如果优化已经触到架构边界，先停下来做边界判断，再决定是否落地。
